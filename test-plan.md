# Sprint 1 Test Plan (S1-TST-01)

This document defines the test plan and pass/fail criteria for Sprint 1 core features, ensuring baseline functionality before deployment.

---

## 1. Landing Page

### Test Case 1.1: Visual and Navigation Load
*   **Action:** Navigate to the base application URL.
*   **Pass Criteria:** 
    *   The page loads within an acceptable timeframe without console errors.
    *   All core structural elements (header, footer, navigation links) are visible.
    *   "Register" and "Login" buttons are clearly accessible.
*   **Fail Criteria:** The page fails to load, displays a server error (e.g., 404, 500), or links are broken.

---

## 2. User Registration

### Test Case 2.1: Successful Account Creation
*   **Action:** Fill out the registration form with a valid email, unique username, and matching strong passwords, then click "Submit".
*   **Pass Criteria:** 
    *   The user account is successfully created in the database.
    *   A success message is displayed or the user is automatically redirected to the dashboard/landing page.
*   **Fail Criteria:** The form submits but no account is created, or a generic system crash occurs.

### Test Case 2.2: Input Validation Failures
*   **Action:** Attempt to register with invalid criteria (e.g., existing email, mismatched passwords, or empty required fields).
*   **Pass Criteria:** 
    *   The form blocks submission.
    *   Clear, user-friendly inline error messages appear (e.g., *"Passwords do not match"* or *"Email already in use"*).
*   **Fail Criteria:** The system accepts invalid data or crashes without explaining what went wrong.

---

## 3. Login / Logout

### Test Case 3.1: Successful User Login
*   **Action:** Enter valid, registered user credentials on the login page and click "Login".
*   **Pass Criteria:** 
    *   The user is successfully authenticated.
    *   The system redirects the user to the authenticated landing page or dashboard.
    *   A session token/cookie is correctly established.
*   **Fail Criteria:** Valid credentials are rejected, or the app logs the user in but fails to redirect.

### Test Case 3.2: Invalid Login Attempt
*   **Action:** Enter an incorrect password or an unregistered email address and click "Login".
*   **Pass Criteria:** 
    *   Authentication is denied.
    *   An explicit error message is displayed (e.g., *"Invalid username or password"*).
*   **Fail Criteria:** The user gains unauthorized access, or the application displays a raw code error stack.

### Test Case 3.3: User Logout
*   **Action:** Click the "Logout" button from the authenticated session.
*   **Pass Criteria:** 
    *   The user session/token is destroyed.
    *   The user is redirected back to the public landing page.
    *   Pressing the browser "Back" button does not return the user to the authenticated dashboard.
*   **Fail Criteria:** The session remains active or the user can still access restricted pages after logging out.

---

## 4. Set / Reset Password

### Test Case 4.1: Password Reset Request
*   **Action:** Navigate to the "Forgot Password" page, enter a registered email, and request a reset link.
*   **Pass Criteria:** 
    *   The application confirms the request was sent (e.g., *"If this email exists, a link has been sent"*).
    *   A reset token or email notification is generated by the system.
*   **Fail Criteria:** The page throws an unhandled error, or explicitly leaks security information by confirming whether an email exists or not.

### Test Case 4.2: Setting a New Password
*   **Action:** Follow the reset link/token process to enter and confirm a new password.
*   **Pass Criteria:** 
    *   The old password is invalidated.
    *   The user can successfully log in using the newly created password.
*   **Fail Criteria:** The user can still log in with their old password, or the new password is not saved properly.
